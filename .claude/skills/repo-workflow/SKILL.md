# 작업 방식 (asdf)

`CLAUDE.md`는 **무엇이** 적용되는지(계층, 게이트, 가드레일)를, 이 스킬은 **어떻게** 일하는지를 말한다.
맥락이 얼마나 찼을 때 핸드오프를 권하는지는 `handoff-trigger` 스킬이다.

## 1. 편집하기 전에 계획한다

- 코드를 먼저 찾고(저장소에 Graft가 있으면 `code-graph` 스킬, 없으면 검색) 영향 분석을 보여준다:
  어떤 파일이 바뀌는지, 무슨 로직이 바뀌고 무엇은 안 바뀌는지, 어떤 게이트가 적용되는지, 이 세션이 그 게이트를
  돌릴 수 있는지.
- **새 모듈·의존성은 사용자와 먼저 정한다**: 선택지, 장기 유지보수 비용(API·형식 안정성, 업그레이드 비용, 도구 종속),
  추천을 가져오고, 사용자가 고른 뒤에 만든다.
- **연결하기 전에 정한다.** 새 연동은 사용자가 받아들인 계획이 있은 뒤에 한다. 계획이 `proposed`면 먼저 받아들여
  (또는 고쳐서 받아들여) 달라고 한다. 아직 정해지지 않은 설계를 위해 쓰지 않는 호출부, 꺼진 워크플로, 빈 껍데기를 넣지 않는다.
- **결정 안내서**는 선택지 2~3개를 표로, 각각의 장기 유지보수 비용, 추천, 열린 질문이다. 사용자가 고르기 전에는
  코드·파일·의존성을 만들지 않는다.
- **바깥으로 나가는 일**(공개 저장소, 테스트용 이슈/PR, 이전, 비밀값, 다른 사람에게 가는 메시지): 하기 전에 무엇이
  만들어지고, 누가 볼 수 있고, 나중에 어떻게 지우는지(그리고 그 권한)를 말한 다음 묻는다. "ok?" 한 마디로는 부족하다.
- 사용자가 "추천대로 해"라고 하면 내가 추천한 것을 한다.

## 2. 실행한다

- 한 번에 한 작업. 파일은 제자리에서 고친다. 이전 도구 출력을 보고 파일을 다시 타이핑하지 않는다(출력이 잘렸을 수 있다).
- **출력은 짧게 - 맥락을 아낀다.** 긴 결과(대조표, 로그, 스모크)는 임시 폴더 파일에 쓰고 개수·불일치·실패만 출력한다.
  게이트(`check.py`)는 로컬에서 테스트·훅 시험 출력을 실패 줄과 개수 줄로 줄이고 전체는 로그 경로에 둔다. 디버그 출력은 필요한 값만 찍는다.
  `output-guard` 훅이 아래 셋을 어기면 실행 전에 경고한다 - 경고를 보면 고쳐 쓰고, 전체가 꼭 필요할 때만 그대로 간다.
  - **검색:** 파일부터(`grep -rl`, `rg -l`), 그다음 그 파일만 줄로. 줄은 자르고 개수를 제한한다(`| cut -c1-200 | head -30`,
    `rg --max-columns 200`) - 데이터 파일은 한 줄이 수백 자다. 호출자·영향 범위는 `code-graph` 스킬로 묻는다.
  - **읽기:** 150줄 넘는 파일은 통째로 읽지 않는다. `grep -n`으로 위치를 찾고 40줄 안팎 범위(읽기 도구 offset/limit, `sed -n`)로 읽는다.
  - **편집:** 있는 파일은 Edit 도구로 바뀌는 줄만 보낸다. 긴 스크립트로 고치면 보낸 글이 맥락에 남고, 읽었던 파일을 셸로 고치면
    바뀐 줄이 알림으로 다시 붙는다. 셸 편집은 여러 파일의 기계적 치환에만. 고친 뒤 파일을 다시 찍어 확인하지 않는다.
- **테스트·골든·병합 보고는 결과만** - 통과/실패 개수, 바뀐 골든, CI·병합 상태. 과정은 서술하지 않는다.
  다만 사용자가 정하지 않았는데 세션이 임의로 정한 것(기준값, 범위, 해석, 건너뛴 것)은 결과와 함께 한 줄씩 밝힌다.

## 3. 정직하게 검증한다

- **게이트가 실패해도 바로 내 변경 탓은 아니다:** 바뀌지 않은 체크아웃(stash 또는 이전 커밋)에서 먼저 돌려 본다.
  없는 도구는 환경이 허락하면 설치하고, 아니면 `NOT VERIFIED`로 남긴다. 멈췄다고 보고하기 전에 내 시간 제한을 확인한다.
- **짧게 여러 번이 아니라 굵게 한 번**(#285). 테스트를 한 번에 다 쓰고 `python tools/check.py --빠른 <새 테스트 파일들>`로
  한 번 실패를 확인한다 -> 구현을 다 한 뒤 같은 명령으로 한 번 통과를 확인한다(실패는 모아서 고치고, 실패한 파일만 다시 돌린다)
  -> push 전에 아래 마무리 한 줄을 한 번 돌린다. 출력은 끝 줄과 `FAILED` 줄만 본다.
- **커버리지 하한은 로컬에서 재지 않는다** - CI(`check`)가 모든 push/PR에서 `python tools/check.py` 전체로 판정한다(로컬 pytest 93초 -> 32초).
  CI가 하한으로 빨갛게 되면 그 PR에서 테스트를 더한다.
- **마무리 한 줄, 골든이 안 바뀐 작업:** `python -m ruff format . && python -m ruff check --fix . && python tools/check.py --빠른`
- **마무리 한 줄, 골든이 바뀐 작업:** `python tools/check.py --골든` - 서식 고침 + `UPDATE_GOLDEN=1` 테스트 전체(직렬) + `golden_diff.py`.
  출력은 FAILED/ERROR 줄과 끝 줄, 파일마다 한 줄 차이 요약뿐이고 전체 출력은 찍힌 로그 경로에 있다(필요할 때만 `grep`).
  갱신 실행은 골든 비교 말고는 모두 단언하므로 마지막 테스트를 겸한다 - 테스트를 다시 돌리지 않는다. 문장 골든은 세션 끝에 자동으로 맞춰진다.
  `.claude/hooks/`를 바꿨으면 끝에 `&& node --test .claude/hooks/*.test.cjs`를 붙인다.
- **같은 실패에 두 번 넘게 매달리지 않는다.** 한 검사가 고칠 때마다 다른 곳에서 깨지면 세 번째를 고치기 전에 멈추고
  공통 원인을 묶어 본 뒤(예: 수치 변경으로 굴림 순서가 밀림), 하나씩 고치기와 한 번에 고치기(예: 굴림 고정)를 비교해 사용자에게 제안한다.
- 막힌 네트워크 호스트는 **우회하지 않고 요청한다**: 호스트 이름과 무엇에 필요한지를 말한다. 미러, 스텁, 손본 의존성을 쓰지 않는다.

## 4. 클라우드 세션 (이 저장소는 주로 여기서 작업한다)

- 컨테이너는 사라진다. 세션을 끝내기 전에 커밋하고 브랜치를 push한다(핸드오프도 마찬가지). 브랜치 이름은 `claude/<작업>`.
- 세션을 시작할 때마다 `CLAUDE.md`의 "처음 한 번"을 다시 한다(도구 설치, `git config core.hooksPath .githooks`).
- GitHub 일(PR, 이슈, CI 확인)은 `gh`가 아니라 GitHub MCP 도구로 한다. Claude가 연 `claude/*` PR은 `auto-merge.yml`이 병합한다(CLAUDE.md "Git").
- 환경 네트워크 정책이 막은 호스트(예: 패키지 저장소) 때문에 설치하지 못한 도구는, 이미 설치된 것으로 게이트를 단계별로
  돌리고 못 돌린 단계는 `NOT VERIFIED: <단계>: <이유>`로 커밋 본문이나 PR에 남긴다. 통과로 쓰지 않는다.

## 5. 상태는 작업 보드에 기록한다 (`CLAUDE.md` "작업 보드")

- 작업은 이슈 하나에서 시작한다. 시작하면 상태를 "지금"으로, PR 본문에 `Closes #N`을 쓴다(병합되면 이슈가 닫혀 "완료").
- 남은 일, 새로 찾은 버그, 돌리지 못한 검증은 이슈로 만든다 - 주인 결정은 담당자 kirnata77, 폰 확인은 검증 `실기기 필요`.
- 로컬은 `gh project item-edit`, 클라우드는 명령 라벨(`명령:상태-지금` 등, 표는 `docs/setup/project-board.md`).

## 6. 브랜치 · 커밋 · push · 메시지

- **PR 본문**: 무엇을 왜 바꿨나, 검증한 것, `NOT VERIFIED`, 헛발질(시도했다 버린 접근 - 길면 이슈 댓글에도).
- 내가 하지 않은 기존 변경은 작업과 관련이 없으면 건드리지 않는다.

### 흐름 - 기능 하나 = 브랜치 하나 = PR 하나 -> `main-branch`

- **`main-branch`에 직접 push하지 않는다.** 기능(버그 수정, 리팩터링 한 단계 포함)마다 `main-branch`에서
  브랜치를 따서 작업한다.
- **PR을 만들기 전에 `git fetch origin main-branch`로 `main-branch`가 최신인지 확인한다.** `main-branch`가 앞서 있으면
  먼저 합쳐서(merge) 충돌을 풀고 게이트를 다시 돌린다. 브랜치도 최신 `main-branch`에서 딴다.
  PR을 열 때 기준 커밋(`origin/main-branch` 해시)을 본문에 적는다.
- **기능이 끝나고 게이트가 통과하면 `main-branch`로 PR을 연다.** 다른 개발자가 `main-branch`의 PR
  목록만 보고 무엇이 왜 들어왔는지 알 수 있어야 한다 - PR 본문에 요점, 이유, 검증한 것,
  남은 것(`NOT VERIFIED` 포함)을 쓴다.
- **Claude가 연 `claude/*` PR은 `auto-merge.yml`이 병합한다**(2026-10-15 결정): Check가 초록이면 병합 커밋으로 병합하고 브랜치를 지운다.
  Claude는 GitHub 자동 병합을 켜지도, 손으로 병합하지도 않는다 - PR 활동을 구독하고 빨간 CI와 리뷰를 고친다. 보호 경로
  (`.github/workflows/`, `buildozer.spec`, `tools/auto_merge_gate.py`, `CLAUDE.md`, `.claude/rules/` - 목록은 그 스크립트의 `PROTECTED`,
  예외는 `UNPROTECTED`: 테스트 지도 `tests.md`와 모듈 배치 `layers.md`는 기능 PR과 같이 자동 병합)를
  바꾸는 PR은 **초안으로 연다.** 초안과 사용자가 연 PR은 사용자가 병합한다(병합할 차례라고 한 번 알린다).
- **병합된 브랜치는 끝난 것이다.** 후속 작업은 최신 `main-branch`에서 새로 시작한다(병합된 브랜치에
  커밋을 더 쌓지 않는다).
- **`main-branch`로 병합된 PR의 브랜치는 이름과 상관없이 자동으로 지워진다**(`.github/workflows/delete-merged-branch.yml`, 워크플로가 병합한 `claude/*`는 `auto-merge.yml`).
  병합 없이 닫힌 PR의 브랜치는 그대로 둔다 - 지우려면 가드레일대로 그 순간 확인을 받는다.

### 커밋 - 한 작업 = 한 커밋, 게이트 통과 후

- **한 문장으로 설명할 수 있는 단위**(계획 한 단계, 버그 하나 수정, 리팩터링 한 걸음)마다
  커밋한다. 파일 하나 고칠 때마다가 아니고, 무관한 작업을 묶지도 않는다.
- **커밋 전에는 관련 테스트, push(와 PR) 전에는 마지막 커밋에서 3절의 마무리 한 줄이 통과해야 한다.** 커밋마다 테스트 전체를
  돌리지 않는다. 그 사이 커밋도 깨진 상태로 두지 않는다. 반쯤 된 작업은 브랜치에 둔다.
- `git status`를 **`git add -A` 전에** 본다. 내가 하지 않은 기존 변경은 작업과 관련이
  없으면 건드리지 않는다.
- **위험한 단계 전에도 커밋한다**(대량 이동, 골든 재작성 등) - 되돌릴 지점을 남긴다.
- 커밋하지 않는 것: `game/saves/`, `.buildozer/`, `bin/`, zip 파일, 비밀값.

### push - 끝까지 검증된 작업만

- **로컬 커밋은 작업 중에 고쳐도 된다**(`--amend`, `rebase`로 합치기/나누기).
- **작업이 끝나고 게이트가 통과하면 push한다**(`git push -u origin <브랜치>`).
- **원격에 올라간 커밋은 고치지 않는다** - 새 커밋으로 수정한다(강제 push 금지).

### 메시지

- **제목은 바꾼 파일이 아니라 변경의 요점**을 쓴다.
  좋음: `전투 판정 함수를 combat_system에서 분리 -- 동작 불변, 골든 그대로`
  나쁨: `Update combat_system.py`
- **본문에는** 6개월 뒤 독자가 복원할 수 없는 것을 쓴다: 무엇을 왜 바꿨는지(이전 믿음을
  고치는 경우 그 믿음이 무엇이었고 무엇을 치렀는지), 무엇을 검증했고 무엇이 아직 열려 있는지.
